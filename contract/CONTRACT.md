# CONTRACT — the shared agreement between the User app and the Admin app

**This `contract/` folder is IDENTICAL in both zips** (`shield-fitness-user` and `shield-fitness-admin`). It is the only thing the two apps share. Neither app imports the other's code. If you can read this folder you know everything the other app expects.

**Contract version: `1.1.0`** (file `contract/VERSION`). `1.0.0` was frozen by Admin Phase 9 on 2026-11-20; `1.1.0` (additive: backups, free accounts, reset) was written by Admin Phase 49 on 2026-11-21. Both zips must carry the identical folder (compare `CHECKSUMS.txt`).

## Rules (binding for every session in either zip)
1. **Never edit `contract/` alone in one zip.** A change needs a `[D]` phase in BOTH zips, the same new `VERSION` in both, and the same file bytes in both. Compare with `sha256sum` (see `contract/CHECKSUMS.txt`, regenerated by the phase that changes anything).
2. **Semver:** patch = wording/fixtures; minor = additive (new optional field, new feature key, new dataset rows); major = breaking. The User app refuses to connect to a gym whose `gym_settings.contract_version` has a different MAJOR.
3. **Everything between the two apps flows through (a) the gym config + policy JSON and (b) Supabase tables/functions listed in `connected-api.md`.** Nothing else. No shared code, no shared build.
4. **The User app must run perfectly with the Admin app absent** (standalone mode). Admin features only ever *add or lock* things; they never become a dependency.
5. **Pure logic is specified here and implemented twice** (once per zip) from the same spec and the same fixtures. Spec: `engines.md`. Fixtures: `fixtures/` (created by the phases named there). A contract test in each zip runs the same fixtures.

## What is in this folder
| Path | What |
|---|---|
| `VERSION`, `CHECKSUMS.txt` | version + file hashes |
| `features.catalogue.json` | every feature switch: key, label, group, default, needs connection, admin-lockable |
| `policy.md` | the policy JSON the Admin app publishes and the User app obeys (locks, defaults, library overrides) |
| `gym-config.md` | the `SFCFG1` connect payload/QR/link and how the User app connects and disconnects |
| `connected-api.md` | tables + Edge Functions the User app uses in connected mode, with owner (who writes/reads); the last part (1.1.0) is backups, free accounts and reset |
| `engines.md` | the shared pure-logic spec: slugs, muscle weights, heatmap, recovery, suggestions, overload, XP; section 27 chunk backup (1.1.0) |
| `fixtures/` | worked examples both apps run: `heatmap_*` (Admin 43), `chunks_*` (Admin 49, hand-worked, unreviewed) |
| `dataset/` | the exercise/machine/muscle data (CSV) + `DATASET_GUIDE.md` |
| `dataset/../images` | machine photos live in each app's `public/machines/`, indexed by `dataset/media_manifest.csv` |

## Naming and id rules (both apps)
- **Slugs:** lowercase kebab, from `slugify()`; exercise/machine slugs come from the dataset and are STABLE ids. Custom (user-made) exercises use `my-<slug>` and a uuid.
- **Muscle ids:** the 34 ids in `dataset/detailed_muscles/muscle_taxonomy_detailed.csv` (core + proposed). Parents roll up to the 17 core ids (`dataset/muscle_taxonomy.csv`).
- **Units:** kg (2 dp), cm, minutes; money in integer paise; dates stored UTC, shown `Asia/Kolkata`.
- **Gym day** = IST midnight.

## Modes
| | Standalone | Connected |
|---|---|---|
| Needs a gym | No | Yes (a gym config was added) |
| Login | None (anyone can use it) | Member login created by an admin |
| Data lives | On the device (backup file) | On the device first, synced to the gym's Supabase |
| Library | Bundled dataset | Bundled dataset + gym policy overrides |
| Admin features | n/a | Locks, defaults, programs, machine status, announcements |
| Install gate | On (phones) | On (phones) |

## Cross-zip dependency map (which phase needs the other zip)
- User Phases 1-64 need NOTHING from Admin, **except live sharing** (User 42): code is built and tested against a mock relay; real sharing starts working once Admin 11 + 15 are deployed and a relay is configured.
- User Phases 65-70 (connection) need Admin Phase 9 (contract frozen, `contract/` re-issued) and Admin Phases 10-18 (SQL, functions, auth, sync) built and deployed by the owner.
- Admin Phases 33-40 (library control) need the User app only through `contract/` (no code).
- **Admin Phase 9 edits `contract/`.** The owner must copy the new folder into the User zip afterwards (compare `CHECKSUMS.txt`).
