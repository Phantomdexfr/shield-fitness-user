# UX_REDESIGN_PLAN: Milestone 11 "Native feel and a calmer UI" (identical copy in both zips)

Written 2026-11-22 from a planning session with the owner. Docs only, no code was changed. User app = Phases 82-88, Admin app = Phases 56-59.
Owner rules still hold (zero cost, dark and gold, offline-first, only admins create passwords, install gate, no store or food log). The THEME stays. What changes is stacking, buttons, density, controls and flows.

## 0. Owner decisions (defaults recorded; the owner can overrule any)
1. Plan share stays plan-only (routines). History, PRs and body stats are never sent. Sending a finished workout is NOT in this milestone.
2. First-run onboarding is shown once to every new standalone user; every optional step has Skip. Gym members (created by an admin) skip the steps already known.
3. Order of work: 82 first (small and safe), then 83, 84, 85, 86, 87, 88.
4. Dates are NEVER typed or entered with the browser's native date input. One shared calendar picker, everywhere, in BOTH apps.
5. Pinch-zoom and double-tap zoom are disabled on touch devices in both apps. Desktop browser zoom is left alone. Body map, atlas and photo viewers keep their own gestures. Later: a "Text size" setting for people who need larger text.

5b. Collapsible sections are in scope for every long page, not only the two the owner named (decided 2026-11-22). Open/closed state is remembered per page (default; the owner may overrule).

## 1. Problems found (evidence from the zips, 2026-11-22)
**P1 No visible Share / Receive for free users.** The feature exists (`src/pages/share/*`, routes `/share`) but `relayAvailable()` is false for a standalone build: `VITE_SHARE_RELAY_URL` is never set (the Deploy workflow passes only `VITE_FREE_SHARDS`, `VITE_CORE_FUNCTIONS_URL`, `VITE_CORE_ANON_KEY`). So `shareOn` is false and the buttons are hidden. For gym members the relay comes from the gym, but the button is buried in a menu on the routine page and "Receive" only exists on the Routines page.
Fix: `relayConfig()` in `src/data/relay/client.ts` falls back to `freeConfig().functionsUrl` and `coreAnon` (project A `/functions/v1`, where `share_create`, `share_status`, `share_claim`, `share_cancel` are already deployed; `ALLOWED_ORIGINS` already has the member origin). No new secret, no function redeploy. `share_*` was NEVER tested (LAUNCH_STATUS section 4): test on two phones.
**P2 Onboarding is missing.** Setup is scattered: Settings > Account has name and birth YEAR only; sex + bodyweight is a separate first-run prompt (`pages/badges/ProfileForm.tsx`); backup consent and password are separate Settings pages. No height, no full date of birth.
**P3 Date entry.** Member app: 6 native `type="date"` inputs (`aiReview/RangeSheet.tsx` x2, `routines/ScheduleEditPage.tsx`, `recap/RecapPage.tsx` x2, `heatmap/HeatmapPage.tsx` x2) plus `account.birthYear` as text. Admin app: typed numeric text in `members.tsx` (from/to), `member-new.tsx` (dob), `TemplateParts.tsx` (start date), `settings.tsx` (holiday date), `audit.tsx` (from/to); grep for more (money, renewals, expiry) before Phase 57.
**P4 Heavy UI.** About 160 `variant="secondary"` and 67 `variant="ghost"` buttons. Ghost has no border and no fill (gold text only) so it reads as plain text; several list links (`sf-lab__link`, `sf-lib__link`, `sf-pr__link`) are plain text rows. Primary is a gold gradient with a glow. Pages stack many cards and button rows (Today: gold card, sync chip, hint card with 3 buttons, 3 more buttons, week view, 2 sheets). Settings are long lists of 4-way segmented rows. ~100 routes, almost none use progressive disclosure.
**P5 Zoom.** Viewport meta is `width=device-width, initial-scale=1, viewport-fit=cover` with no zoom limit and no `touch-action` on html/body, so pinch and double-tap zoom work. Manifest is already `orientation: portrait`.
**P6 Heatmap and body figure ignore the profile.** `HeatmapPage.tsx` and `MarksPage.tsx` start with `useState<Sex>('male')` and show their own Male/Female toggle. `getProfile().sex` (`'m' | 'f' | 'unspecified'`) is never read there. Wherever a body figure is drawn (BodyPicker, heatmap, marks, recovery, muscle lab, atlas, admin `BodyFigure`) it must follow the profile.

## 2. The new look: design spec (the owner approved the mockup; values below are the source of truth)
Tokens stay (`src/ui/styles/tokens.css`): bg `#0d0c0a`, raised `#15130f`, line `#2e2a20`, line-strong `#4a4332`, text `#f4eedc`, text-2 `#bdb49c`, muted `#9a917b` (use `#9a917b`, not `#857d69`, for small text: contrast), gold `#d4af37`, on-gold `#120f06`.
**Buttons (the only four kinds; delete the rest):**
- Primary: solid `#d4af37`, text on-gold, 48px high (50 on full-screen flows), radius 12, weight 700, NO gradient, NO glow. At most ONE per screen.
- Secondary: transparent, 1px `line-strong` border, text `#f4eedc`, 40px high (44 minimum touch height is kept by padding the hit area), radius 10, weight 600.
- Destructive: 1px `--danger` border and text. Never the primary.
- Navigation rows: a row inside a bordered group, label left, value or chevron right, 52px high. This REPLACES every borderless "ghost" text button. A "Skip" or "Cancel" is a Secondary button, never bare text.
- Icon buttons: 40px, 1px border, radius 12.
**Surfaces:** one card style (raised bg, 1px `line`, radius 14-16). Emphasis = `line-strong` border or gold label, not shadows or glow. Section labels: 12px uppercase, letter-spacing 0.06em, muted.
**Controls (replace the 4-way segmented rows):** 2 options = small segmented toggle (kg/lb style); 3 options = segmented; 4 or more = a row showing the value with a chevron that opens a bottom sheet list (a "combobox"); on/off = switch with a clear on state (gold track). Numbers (height, weight, rest seconds) = row that opens a wheel/stepper sheet; never a free text box for a number that has a sane range.
**Density:** page padding 16, section gap 16, row gap 8, inside cards 14-16. Text 15px body, 12-13px meta. Tab bar 64px with outline icons and a gold active state.
**One main action per screen.** Secondary actions: 2-up grid of Secondary buttons, or a "More" sheet. Hints, banners and welcome cards are collapsed into ONE slot on Today.
**Collapsible sections (owner request 2026-11-22):** every long page shows its first, most important block open and everything below it as stacked, closable sections. One shared `Collapsible` component: a bordered bar (same card style), 48px high, title left, a short summary right (for example "6 exercises", "3 setups"), chevron that rotates; tap opens or closes it with a short animation (respect reduced motion); header is a real `<button>` with `aria-expanded`. Several can be open at once. Open/closed state is remembered PER PAGE (a small pref keyed by route + section id; default = recorded below), and a "Collapse all" / "Expand all" link sits at the top of any page with 4 or more sections. Default open: the primary block only (on a live workout: the current exercise and its set logger stay open; notes, history, setup options, tips and the rest start closed). Applies to ALL pages that scroll past one screen: Library (list filters), Exercise page (muscles worked, setup options, movement map, history and records, notes, similar exercises), Machine page, Machine index and Machine Lab, Muscle page, Routine week and day, Session and its summary, History, Records, Progress hub and its detail pages, Body/Recovery/Marks, Heatmap options, Goals, Gym home, Backup home, Settings group pages. Guard test: a page component may not render more than 3 top-level sections that are always open (listed exceptions only).
**Today screen target:** header (date label + title + small sync pill) / one workout card (label, name, meta, Start workout, 2-up Swap day + Rest today) / this-week strip (7 outlined cells, today gold outline) / "Quick" 2x2 grid (Share plan, Scan plan, History, Quick workout) / tab bar.
**Calendar picker (shared component, no native date input):** bottom sheet; two dropdown chips (Month, Year; year list jumps, newest first, for birth dates start in a sensible past year); weekday header Mon-first; 7-column day grid, 42px cells; selected day solid gold; Cancel (secondary, 1/3) + "Set 12 Mar 1998" (primary, 2/3). Works offline, keyboard and screen reader labelled, honours min/max (e.g. from <= to). Pure date logic goes in `src/shared/` (both apps keep their own copy; the guard test compares them like `contract/`), UI in each app's `ui/`.
**Onboarding screen target ("About you", step 3 of 5):** back icon button + 5-segment progress bar; title + one plain sentence; Male/Female segmented toggle; a body preview panel (250px) that shows the chosen figure immediately; a bordered group of 3 rows: Date of birth (opens calendar), Height (cm, sheet), Weight (kg or lb, sheet); Continue (primary) + "Skip for now" (secondary).

## 3. Onboarding flow (Phase 85)
1. Welcome + name (display name) and a username (only if the user turns backup on; otherwise not asked).
2. Date of birth (calendar picker; replaces `account.birthYear`, which stays readable for old installs and is derived from the full date).
3. About you: sex (male / female; "prefer not to say" maps to the male figure with a visible Switch figure link and the existing Estimated badge rule), height, weight, units (kg/lb, cm/ft).
4. Training: level (beginner / intermediate / advanced) as a dropdown row.
5. Backup: "Turn on free backup" (then username and password generation using the EXISTING `BackupConsent` and `BackupPassword` pages) or "Not now", with the plain risk text: "If you lose, reset or reinstall this phone, your workouts are gone." Never auto-enable.
6. Optional: "Join a gym" (scan the gym QR, existing `GymAddPage`).
Rules: one question group per screen, progress bar, Back always works, Skip on every optional step, resume where left off after an app kill, runs once (flag in prefs), re-runnable from Settings > Account. Gym members whose name, sex or dob came from the gym skip those steps. Height and date of birth are NEW fields: add them to the profile prefs, to the backup/restore payload, and (if the gym should see them) to `contract/` as a minor bump with an Admin phase. DEFAULT: keep them local + in backup only; do NOT change `contract/` in this milestone unless Phase 85 proves it is needed (then stop and say so).

## 5. How to ship (unchanged, see LAUNCH_STATUS section 6)
Member: edit, `git add -A`, `git commit`, `git push`, then GitHub > Actions > Deploy > Run workflow. Admin: `git push` (Vercel auto-deploys). NO Edge Function redeploy is needed by Milestone 11 unless a phase changes `supabase/functions` or a file they import (`src/shared/*.ts`): if so, redeploy as LAUNCH_STATUS section 6 says. No SQL is needed.
The earlier standing rule holds: change one phase at a time, owner tests on a real phone, then the next phase.

## 6. Risks
- Disabling zoom hurts low-vision users: the Text size setting is queued (not in this milestone) and the owner accepted the trade-off.
- iOS ignores `user-scalable=no`; the `touch-action` + `gesturestart` parts do the work there. Untested on iPhone until the owner has one.
- A visual redo touches ~100 screens; ship Phase 83 first so later phases are mostly swapping components, and keep screenshots.
- Native `type="date"` removal must not break existing saved dates: values stay ISO strings.
- The share relay fallback uses project A's functions: the first real use of `share_*`; if it fails check Logs > API Gateway on project A first (LAUNCH_STATUS section 6).
